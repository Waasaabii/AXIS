# 协议适配规则学习与用户确认

## 核心目标

AXIS 需要持续适配代理协议、订阅格式和客户端差异。协议生态会变化，订阅中可能出现新字段，Shadowrocket、Mihomo、Sing-box、其他 AXIS 对同一协议的字段表达也可能不同。

LLM 的作用不是直接控制代理运行，也不是直接修改代码，而是帮助 AXIS 识别协议差异、生成适配规则草案和测试建议。LLM 输出必须是 AXIS 可消费的结构化草案，不是让用户手工照抄的配置说明。

协议规则学习不是炫技能力。只要 AXIS 支持导入第三方订阅并再次发布，就必须面对字段丢失问题。写死解析和发布规则会把兼容成本转嫁给用户，导致“导入成功但二次发布后不可用”。

例如某些订阅可能包含：

- Trojan 的 `sni`、`peer`、`allowInsecure`。
- VMess 的 `ws`、`host`、`path`。
- Hysteria2 的 `obfs`、`alpn`、`insecure`。
- 客户端提示、套餐信息、剩余流量等非节点条目。

如果 AXIS 当前规则只保存 `type`、`server`、`port`、`password` 等最小字段，二次发布给 Shadowrocket、Mihomo 或其他 AXIS 时就可能丢失必要参数。LLM 在这里的价值是帮助 AXIS 发现差异、解释风险、生成可测试草案，让用户决定是否采用，而不是让用户自己研究协议细节。

核心目标：

```text
发现未知或不兼容格式 → LLM 生成规则草案 → AXIS 生成临时规则 → 用户测试 → 用户确认 → 固化启用
```

## 职责边界

### LLM 可以做

- 分析订阅样本中的未知字段。
- 判断字段可能属于哪个协议能力。
- 对比 AXIS 当前解析结果，指出丢失字段。
- 生成协议适配规则草案。
- 生成测试样例和验证清单。
- 解释规则风险和适用范围。
- 建议目标客户端输出格式，例如 Mihomo YAML 或 Shadowrocket URI。

### LLM 不可以做

- 直接修改 AXIS 运行时代码。
- 直接启用新协议规则。
- 直接改系统配置、nginx、宝塔、防火墙或代理核心配置。
- 绕过 AXIS 的确定性测试。
- 把未经验证的规则用于正式发布。
- 替代 AXIS 的确定性解析器、渲染器和连通性检查。

## 推荐流程

协议适配规则学习必须使用可追溯状态流：

```text
发现问题
  ↓
生成建议
  ↓
待测试
  ↓
测试中
  ↓
测试通过 / 测试失败
  ↓
用户确认采用 / 用户放弃
  ↓
已启用 / 已回退
```

任何 LLM 输出的规则都必须先作为临时规则存在。只有测试通过并且用户明确确认后，才能固化为正式规则。

## 触发场景

可以触发协议规则学习的场景：

- 订阅源出现 AXIS 未识别字段。
- 导入订阅后节点在目标客户端不可用。
- Mihomo 可用但 Shadowrocket 不可用。
- Shadowrocket 可用但 Mihomo 不可用。
- 二次发布后节点缺少必要参数。
- 某协议出现新客户端字段或新 URI 参数。
- 用户手动提交失败样本请求分析。

## 第一阶段范围

第一阶段必须解决“发现和提示字段丢失”，但不要求一次性完成完整自动固化流水线。

第一阶段应该做：

- 保存原始分享链接。
- 保存 AXIS 暂不理解的扩展字段。
- 对比原始节点和当前解析结果，发现丢失字段。
- 对比当前发布输出，发现目标客户端可能缺少的字段。
- 用 LLM 分析字段含义和兼容风险。
- 生成可读的适配建议。
- 生成临时规则草案。
- 让用户测试、采用或忽略。

第一阶段不应该做：

- 让 LLM 自动修改 Go/JS 代码。
- 未经测试直接启用规则。
- 自动覆盖全部客户端输出。
- 自动把所有未知字段都发布出去。
- 把未经验证的规则写入正式配置。

后续阶段再考虑：

- 规则引擎自动解释和应用更多协议。
- 多客户端完整回归测试。
- 协议规则版本管理和灰度启用。
- 规则市场或远程规则更新。

## 核心版本与能力检测

AXIS 不应假设代理核心版本固定。用户可以单独升级 Mihomo 或未来其他核心，因此 AXIS 的协议能力不能只依赖写死版本表。

AXIS 必须区分两类能力：

- 核心能力：当前代理核心实际支持什么协议、字段、出站、入站或 listener。
- AXIS 模板能力：AXIS 当前是否会解析、保真、渲染、发布和创建对应协议。

用户更新 Mihomo 后，AXIS 应重新检测：

- 核心版本。
- 可用出站协议。
- 可用入站或 listener 协议。
- 配置校验结果。
- 关键字段是否被当前核心接受。

当核心已支持某个协议或字段，但 AXIS 暂无模板时，AXIS 可以提示：

```text
检测到当前核心可能支持新的协议能力，但 AXIS 尚未有对应模板。可以生成测试模板，测试通过后再采用。
```

LLM 可以参与调研核心文档、订阅样本和客户端格式，生成模板草案；AXIS 必须通过配置校验、临时实例或连通测试确认后，才允许用户采用。

## 协议支持层级

“支持协议”必须拆成层级展示，不能简单显示支持或不支持。

推荐层级：

- 导入：AXIS 能识别该协议或保留原始链接。
- 保真保存：AXIS 能保存必要字段和未知扩展字段。
- 发布给客户端：AXIS 能输出 Mihomo、Shadowrocket 或其他 AXIS 可用格式。
- 本机使用：当前代理核心支持该协议出站，AXIS 能生成可运行配置。
- 创建本机节点：当前代理核心支持服务端入站或 listener，AXIS 能生成本机节点配置和连接信息。
- 诊断测试：AXIS 能对该协议执行必要可达性或连通性检查。

示例：

```text
协议 X
- 导入：可尝试
- 保真保存：支持
- 发布给 Shadowrocket：待测试
- 本机使用：取决于当前 Mihomo 是否支持出站
- 创建本机节点：暂不支持，除非核心支持对应 listener
```

如果底层核心不支持出站，AXIS 不能承诺本机使用。若底层核心不支持入站或 listener，AXIS 不能承诺创建本机节点。

## 模板分层

协议模板应按能力分层，不要把“支持协议”做成一个不可拆的开关。

推荐模板层级：

```text
parse
preserve
publish/mihomo-yaml
publish/shadowrocket-uri
runtime/mihomo-outbound
runtime/mihomo-inbound-or-listener
axis-import
tests
```

某个协议可以先支持导入和保真，再逐步支持发布、本机使用和本机创建。用户界面必须展示当前支持到哪一层。

## LLM 输入

发送给 LLM 的输入应经过脱敏和裁剪，至少包含：

- 协议类型。
- 目标客户端。
- 原始节点样本的脱敏版本。
- AXIS 当前解析结果。
- AXIS 当前输出结果。
- 失败现象。
- 已执行的测试结果。
- 已知客户端要求。

敏感内容必须脱敏，例如：

- 密码。
- UUID。
- token。
- 用户账号。
- 私有订阅地址。

## LLM 输出

LLM 必须输出结构化规则草案，不输出可直接执行代码，也不输出需要用户手工拼接的配置。AXIS 应根据结构化草案生成临时规则、模板、测试项和确认卡片。

推荐结构：

```json
{
  "protocol": "hysteria2",
  "target_client": "shadowrocket",
  "output_format": "uri",
  "status": "proposal",
  "required_fields": ["password", "server", "port", "sni"],
  "preserve_fields": ["sni", "insecure", "obfs", "alpn"],
  "query_params": {
    "sni": "sni",
    "skip_cert_verify": "insecure"
  },
  "uri_template": "hysteria2://{password}@{server}:{port}/?{query}#{name}",
  "risks": [
    "缺少 sni 时可能无法通过证书校验"
  ],
  "tests": [
    {
      "name": "保留 sni 参数",
      "input_protocol": "hysteria2",
      "expected_contains": ["hysteria2://", "sni="]
    }
  ]
}
```

AXIS 只能把该输出当作规则草案，再由规则引擎解释和验证。

## 流式输出

LLM 调用应优先支持流式输出，但流式过程只能用于展示分析进度和中间发现，不能边输出边修改配置。

流式输出应分为两层：

- 进度事件：给用户展示，例如正在分析字段、发现未知参数、正在生成测试项。
- 最终结果：完整结构化 JSON，供 AXIS 校验和生成临时规则。

流程必须是：

```text
流式分析进度
  ↓
完整 JSON 输出
  ↓
AXIS schema 校验
  ↓
生成临时规则或模板
  ↓
测试
  ↓
用户确认
  ↓
固化启用
```

禁止使用流式半截结果直接启用规则或修改配置。

## 测试要求

规则固化前必须测试。测试至少分为：

- 格式测试：确认 URI 或 YAML 能正确生成。
- 字段保真测试：确认必要字段没有丢失。
- 转义测试：确认名称、密码、路径和查询参数编码正确。
- 回归测试：确认原有客户端输出没有被破坏。
- 导入测试：确认 AXIS 自己能反向解析生成结果。
- 连通测试：在可行时验证代理请求可以成功。

无法自动完成的客户端测试，应生成临时订阅链接，让用户在客户端中手动测试。

## 用户确认

用户测试前，前端只展示用户能理解的信息：

- AXIS 发现了什么问题。
- 新规则准备解决什么。
- 这个规则适用于哪个协议和客户端。
- 需要用户怎么测试。
- 测试通过后是否采用。

用户确认文案应类似：

```text
测试通过后，AXIS 将以后使用这个规则生成 Shadowrocket 的 Hysteria2 连接。
```

不要展示内部字段堆砌，除非用户打开高级详情。

## 固化与回滚

规则采用后必须可追溯：

- 规则 ID。
- 协议。
- 目标客户端。
- 来源：LLM 生成、人工确认。
- 测试结果。
- 启用时间。
- 确认人或确认动作。
- 上一个可回滚版本。

规则启用后必须支持回滚。回滚时恢复上一版规则，不影响节点来源、线路组合和发布项本身。

## 数据模型建议

协议适配规则可以使用类似结构：

```json
{
  "id": "shadowrocket-hy2-uri-20260424",
  "protocol": "hysteria2",
  "target_client": "shadowrocket",
  "source": "llm",
  "status": "pending_test",
  "proposal": {},
  "test_results": [],
  "enabled": false,
  "created_at": "2026-04-24T00:00:00Z",
  "approved_at": null,
  "rollback_to": null
}
```

状态建议：

- `draft`：刚生成，未准备测试。
- `pending_test`：等待用户或 AXIS 测试。
- `testing`：测试中。
- `test_passed`：测试通过，等待用户确认。
- `test_failed`：测试失败。
- `approved`：用户确认采用。
- `enabled`：已启用。
- `rejected`：用户放弃。
- `rolled_back`：已回退。

## 安全要求

协议自更新不能绕过安全边界：

- 默认不自动发送完整敏感订阅给 LLM。
- 默认不让 LLM 生成可执行系统命令。
- 默认不让 LLM 生成 Go/JS 代码并直接运行。
- 默认不自动启用未测试规则。
- 规则解释器必须限制可用字段、模板能力和输出范围。
- 规则测试失败时不得影响已启用规则。

## 与节点保真的关系

协议规则学习依赖节点字段保真。AXIS 必须先保存原始分享链接和扩展字段，才有能力在未来生成新的适配规则。

如果导入阶段已经丢失字段，LLM 也无法可靠恢复协议能力。
