# AXIS 数据与 API 模型约束

## 分层归属

默认业务归属：

```text
节点来源 → 线路组合 → 使用 / 发布
```

后端、API 和配置渲染应围绕这个归属收敛，避免同一语义出现多套实现。

## 节点来源模型

节点来源应覆盖：

- 订阅。
- 单个代理。
- 其他 AXIS 连接。
- 本机节点。

本机节点是节点来源类型之一，不应以完全独立的数据模型绕过节点来源管理。

节点来源应能表达来源模式：

- 上游模式：订阅、单代理、其他 AXIS。重点是保真保存、同步、健康检查和发布适配。
- 本体模式：本机节点。重点是 AXIS 生成服务配置、认证、端口、协议参数和可达性检查。

上游节点不要只保存最小连接字段。模型应支持保存原始分享链接、原始解析结果和扩展参数，避免二次发布时丢失上游伪装能力。

订阅源应至少保存：

- 订阅地址。
- 启停状态。
- 同步间隔。
- 上次同步时间。
- 上次同步结果。
- 上次成功快照。
- 失败原因。
- 下一次允许失败触发刷新的时间。
- 解析出的节点列表和信息类条目。

## 线路组合模型

线路组合应统一承载：

- 初始代理。
- 落地出口。
- 自动选择。
- 手动选择。
- 顺序容灾。
- 健康检查。
- 中转组合。

使用和发布都应引用线路组合结果，不应复制线路选择规则。

## 使用模型

使用模型应表达本机当前怎么用：

- 本地代理启停和地址。
- 虚拟网口启停和状态。
- 当前使用线路。
- 当前节点或路径摘要。
- 应用更改状态。

使用模型不应保存独立于线路组合之外的第二套路由规则。

## 发布模型

发布模型应表达把哪条线路以什么形式提供给外部：

- 发布类型：HTTP 代理、订阅链接、AXIS 连接等。
- 绑定线路。
- 认证信息。
- 访问范围。
- 启停状态。
- 连接信息。

对外发布默认必须认证。认证规则归属于发布模型，不应散落到线路组合或使用模型中。

## 协议适配规则模型

协议适配规则用于描述某个协议如何面向某个客户端输出，例如 Mihomo YAML、Shadowrocket URI 或其他 AXIS 可导入格式。

规则可以由内置版本提供，也可以由 LLM 生成草案，但 LLM 生成的规则不能直接启用。

规则模型应至少表达：

- 规则 ID。
- 协议。
- 目标客户端。
- 输出格式。
- 来源：内置、人工、LLM。
- 状态：草稿、待测试、测试通过、已确认、已启用、已回退。
- 规则草案。
- 测试结果。
- 启用时间。
- 回滚目标。

协议适配规则必须与节点来源、线路组合、发布项解耦。更新规则不应直接改动节点来源或线路组合，只影响后续解析、渲染或发布适配结果。

## 核心能力模型

AXIS 不应假设代理核心版本固定。用户可以单独升级 Mihomo 或未来其他核心，因此需要记录当前核心能力。

核心能力模型应至少表达：

- 核心名称。
- 核心版本。
- 检测时间。
- 支持的出站协议。
- 支持的入站或 listener 协议。
- 已验证字段或配置片段。
- 配置校验结果。
- 临时实例测试结果。
- 该能力对应的 AXIS 模板状态。

协议支持状态应分层表达：

- 导入。
- 保真保存。
- 发布给目标客户端。
- 本机使用。
- 创建本机节点。
- 诊断测试。

如果核心支持但 AXIS 模板缺失，应进入“可生成模板草案”的状态，而不是直接显示不支持。

## 自适应出口规则模型

自适应出口规则用于描述某个目标、场景或异常应如何选择直连、代理或出口池。

规则可以由用户手动创建，也可以由 LLM 根据自然语言、已有节点和运行特征生成草案。LLM 生成的规则必须先由用户确认或经过明确自动模式授权，不能在运行时直接由 LLM 决策。

规则模型应至少表达：

- 规则 ID。
- 规则名称。
- 来源：用户手动、模板、LLM。
- 状态：草稿、待确认、已启用、已禁用、已回退。
- 作用范围：域名、域名后缀、目标分类、应用场景或异常类型。
- 匹配条件。
- 动作：直连、使用出口池、排除出口、临时切换、提醒确认。
- 优先级。
- 有效期或冷却时间。
- 测试结果。
- 用户确认记录。
- 回滚目标。

运行特征模型应至少表达：

- 目标域名或脱敏目标。
- 目标分类。
- 当前入口和出口。
- 出口标签。
- 节点来源。
- 协议。
- 连接结果和异常类型。
- DNS、TCP、TLS、UDP 检查摘要。
- HTTP 状态码和可识别风控信号。
- 延迟、失败次数、切换结果。
- 采集时间和聚合窗口。

默认不得保存页面正文、请求体、Cookie、登录信息、完整查询参数或其他敏感内容。

## API 命名建议

API 命名优先体现产品语义，而不是底层实现名：

- `nodeSources` 表示节点来源。
- `routes` 或 `paths` 表示线路组合。
- `usage` 表示本机使用状态。
- `publications` 表示发布项。

如果历史代码已有 `provider`、`egress_group`、`listener` 等命名，新增能力应优先在业务层收敛语义，再由适配层处理历史结构。

## 本机节点部署字段建议

本机节点作为 `node_sources[]` 的一种类型，应至少表达：

- 协议：HTTP、SOCKS、Trojan、Hysteria2。
- 访问方式：宝塔/nginx 反向代理，或直接开放端口。
- 监听地址：`127.0.0.1` 或 `0.0.0.0`。
- 本机端口。
- 认证信息。
- 绑定线路。
- 可选外部域名，仅用于生成连接信息和检查，不作为宝塔/nginx 的配置来源。

数据模型不要默认保存宝塔账号、宝塔面板地址或云厂商凭据。AXIS 第一阶段只提示用户如何配置，不自动接管宝塔或云安全组。

本机节点创建流程还应能表达创建方案草案：

- 创建目标。
- 推荐协议组合。
- 推荐监听地址和端口。
- 推荐发布格式。
- 环境检测摘要。
- 测试项和测试结果。
- LLM 方案来源和置信度。
- 用户确认状态。
- 创建后加入的出口池。

创建方案草案不等于已启用配置。只有测试通过并经用户确认后，才写入正式节点来源和出口池。

## 可达性检查模型

本机节点和发布项应具备检查结果模型，至少表达：

- 检查项名称。
- 当前状态：通过、提醒、失败、未知。
- 用户能做什么。
- 检查时间。

Hysteria2 必须有 UDP 可达性检查项。Trojan 必须有 TCP 端口、域名和证书相关检查项。
